My T03 Implementation

The SQLite database is stored as a file-backed .db file whose path is supplied
to the ResidentRepository constructor, so the location is configurable rather
than hard-coded. The ResidentRepository class in src/repositories/ResidentRepository.js
handles all Resident persistence. When save() is called, it prepares a
parameterized INSERT statement that supplies the six Resident fields excluding
id, executes it, and then reads the database-generated identifier from
result.lastInsertRowid, assigning it back to resident.id. The ID is always
generated by SQLite through AUTOINCREMENT on the primary key column, never
assigned manually in JavaScript. findById() prepares a SELECT statement with
a single id parameter, executes it with stmt.get(), and if a row is found,
maps the database columns back into a new Resident instance using the existing
Resident constructor. If no row is found, findById() returns null so that
callers can handle the not-found condition without the application crashing.


My Persistence Design Decision

I decided to separate the database connection and table initialization into
two dedicated modules: src/database/database.js and src/database/migrate.js,
rather than placing that logic directly inside ResidentRepository.js or app.js.
I implemented it this way because it keeps each module focused on a single
responsibility — database.js only opens the connection, migrate.js only
creates the schema, and ResidentRepository.js only handles queries. This also
makes it easy for tests to inject a different database path without touching
the repository logic. The alternative I considered was putting everything
inside the ResidentRepository constructor, but that would have made the
repository harder to test and harder to understand.


My Database Initialization Design

Database initialization file or module: src/database/migrate.js
Where the database path comes from: passed as a constructor argument to ResidentRepository
How the Resident table is initialized: migrate(db) calls db.exec() with a CREATE TABLE statement
How repeated initialization is handled: the SQL uses CREATE TABLE IF NOT EXISTS so running it multiple times is safe

I designed it this way so that database initialization is repeatable and
non-destructive. Using IF NOT EXISTS means the application can call migrate()
on every startup without risking data loss or a duplicate-table error. Keeping
the path as a parameter rather than a hard-coded string means automated tests
can supply a temporary file path, keeping test data completely isolated from
the development database.

SQL I Can Explain

INSERT INTO residents (first_name, last_name, address, contact_number, email, status)
VALUES (?, ?, ?, ?, ?, ?)

This statement inserts one new row into the residents table. The id column is
excluded so that SQLite generates it automatically via AUTOINCREMENT. Each ?
is a positional parameter supplied at runtime: the first ? receives
resident.firstName, the second resident.lastName, the third resident.address,
the fourth resident.contactNumber, the fifth resident.email, and the sixth
resident.status. Using parameters instead of string concatenation prevents
SQL injection. This statement is used inside the save() method of
ResidentRepository.


My Resident Mapping

When findById() retrieves a row from SQLite, the raw row object uses the
database column names such as first_name and contact_number. These do not
match the JavaScript property names firstName and contactNumber used by the
existing Resident model. To convert the row into a Resident instance, I pass
a mapping object to the Resident constructor, explicitly translating each
column: row.first_name becomes firstName, row.last_name becomes lastName, and
row.contact_number becomes contactNumber. The remaining columns which are id, address,
email, and status, share the same name in both the database and the model.
The result is a proper Resident instance that application code can use with
resident.firstName, resident.contactNumber, and so on.


Problem I Encountered

Problem or error: TypeError: stmt.close is not a function
Cause: Node.js 26 prepared statements from node:sqlite do not expose a close() or finalize() method. I assumed those methods existed based on other SQLite libraries.
How I resolved it: I asked Amazon Q, an AI coding assistance, what might be wrong with my code snippet. Then it inspected the actual prototype of a prepared statement at runtime using Object.getOwnPropertyNames() and confirmed that neither method exists. I then removed all stmt.close() and stmt.finalize() calls since Node.js manages statement cleanup automatically.


My Student-Designed Test

Test name: manually set id is ignored, SQLite generates its own
What it verifies: That even if a Resident object is constructed with a pre-set id value, the repository ignores it during INSERT and SQLite still generates a new unique identifier. The saved id will not collide with an existing record.
Why I chose this scenario: I wanted to confirm that the persistence layer never allows JavaScript code to override the database-generated primary key. This could detect a defect where the INSERT accidentally includes the id column, which could cause a primary key conflict or silently overwrite an existing record.
